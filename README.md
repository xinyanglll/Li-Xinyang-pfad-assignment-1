# Why Are We Here?

Before taking this course, I had never formally learned programming languages such as Python, JavaScript, C#, or Processing. As an interaction design student, most of my previous work focused on visual and interaction design. I mainly used Figma, Adobe, Blender, and TouchDesigner, and I had relatively little experience with Unity. Because of this background, I used to see programming as something technical and separate from the design process.

However, I had already encountered programming indirectly in one of my previous projects. I once worked on a pet health AI recognition feature, where the code was generated with the help of AI based on my design requirements. At that time, I was mainly concerned with what the feature should do and how users would interact with it. I could use AI to produce working code, but I did not fully understand the logic behind that code.

This made me wonder: **if AI can already write code for me, why should I still learn programming?**

The Schotter exercise challenged this assumption. I thought code required a large amount of input just to produce a working program. I mainly understood code as something that serves a system: it makes a function work, but it is not something I would directly experience as a designer. I did not realise that code could also have so many forms of expression. In the Schotter exercise, I saw code produce a visual pattern rather than simply a functional system. This changed how I understood programming as a medium. Dylan Beattie describes code as something that can be expressive and creative, rather than only a technical tool (Beattie, 2020). My own experience with Schotter made this idea more concrete. When I changed the `CHAOS` parameter from `1.0` to `2.0`, the squares became more rotated and scattered. The fact that such a small change in the code could create a visible change in the result was surprising to me. For the first time, I began to see programming not only as a technical tool, but also as a creative material.

The experience also made me think differently about AI-generated code. AI can already help me produce a working solution from a description, but producing code is not the same as understanding it. If I only tell AI what I want and accept whatever it gives me, I may be able to create something that works without really knowing why it works. More importantly, I may not know what to change when the result is wrong or when I want to create something different.

For an interaction designer, this distinction matters. I do not necessarily need to compete with AI in writing code line by line. Instead, I need enough programming knowledge to read what it produces, question its decisions, change its behaviour, and understand what is possible. Otherwise, AI becomes a black box between my idea and the final experience.

This does not mean that I need to become a professional programmer. My argument is that, for a designer working with AI, learning programming is increasingly less about writing every line of code and more about developing the ability to understand, evaluate, and shape computational systems. I want to be able to look at a piece of code and understand the relationships behind it, rather than treating it as something mysterious that only needs to work. I also want to use code to explore ideas that would be difficult to express through conventional design tools.

So, why are we here? For me, the answer is not that AI cannot program. It can, and it will probably become much better at it. That is exactly why I think learning programming is valuable. When machines become better at producing code, the important skill may shift from simply writing instructions to knowing what should be asked, what should be questioned, and what should be changed. As a designer, I want to understand my materials well enough to shape them rather than simply request an outcome from a black box. Programming gives me another material to think and design with.
